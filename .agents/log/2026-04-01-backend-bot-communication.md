# Принцип зв'язку Backend та Telegram Bot

Статус: done

## Рішення
Взаємодія між основним FastAPI бекендом та Telegram ботом побудована на двох незалежних механізмах:

1. **HTTP API Запити (Бот -> Бекенд)**
   Бот виступає як клієнт і звертається до бекенду через REST API для отримання або зміни даних. Це синхронний зв'язок, що використовується, коли ініціатором дії є користувач (наприклад, перевірка статусу перепустки, створення заявки на парковку).

2. **Redis Streams (Бекенд -> Бот)**
   Бекенд використовує Redis Streams для асинхронної відправки нотифікацій та подій боту. Бот має постійно працюючого слухача (stream listener), який миттєво реагує на нові повідомлення. Це використовується, коли ініціатором є система або адміністратор/охорона в дашборді (наприклад, сповіщення охорони про нову заявку, повідомлення користувача про зміну статусу його перепустки).

## Чому
Такий гібридний підхід забезпечує надійність та продуктивність:
- **HTTP API** зручно для операцій типу Request-Response, де боту одразу потрібен результат.
- **Redis Streams** ідеально підходить для подієво-орієнтованої архітектури (Event-Driven). Це усуває необхідність постійного опитування (polling) бекенду ботом. Повідомлення зберігаються в Redis, тому навіть якщо бот тимчасово впаде, він прочитає пропущені події після перезапуску.

## Зачеплені файли/модулі
- **HTTP API:** `telegram-bot/src/api.py` (клієнт в боті), `backend/src/routers/*` (роути бекенду).
- **Redis Streams:** `backend/src/redis.py` (публікація подій), `telegram-bot/src/services/stream_listener.py` (слухач подій в боті).
