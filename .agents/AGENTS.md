## 1. Огляд проєкту та його призначення

**Visitor Management System (VMS)** — це цифрова платформа для автоматизації та контролю доступу на територію житлового комплексу. Основна мета системи — спростити взаємодію між мешканцями та службою охорони під час замовлення перепусток.

### Основні сценарії використання:
1. **Мешканець** створює запит на гостьову перепустку (для пішохода, таксі, авто або кур'єра) через зручний інтерфейс у Telegram-боті.
2. **Охорона** миттєво отримує сповіщення про нову заявку на веб-панелі (дашборді) через WebSocket-з'єднання.
3. **Охорона** підтверджує або відхиляє запит.
4. **Бот** надсилає мешканцю статус виконання заявки (через Redis Stream `vms_stream`).
5. **Планувальник** (APScheduler) автоматично перевіряє та переводить застарілі заявки у статус `EXPIRED` кожні 60 секунд.

### Потік даних (як це працює технічно)
- Backend — єдине джерело істини для стану заявок (PostgreSQL). Bot і Frontend ніколи не зберігають стан самостійно.
- Backend → Bot: асинхронне сповіщення виключно через Redis Stream `vms_stream`; пряме звернення backend → bot HTTP-запитом не використовується.
- Bot → Backend: усі запити йдуть через HTTPX-клієнт до FastAPI роутерів, автентифікація через Telegram `initData`.
- Frontend (дашборд охорони) отримує оновлення в реальному часі через WebSocket (`services/websocket_manager.py`), REST — лише для початкового завантаження та дій (підтвердити/відхилити).
- FSM-стан діалогу бота живе виключно в Redis (`RedisStorage`), ніколи в пам'яті процесу.

## 2. Технологічний стек

Проєкт побудовано на базі сучасного та швидкого стеку технологій:

* **Backend**:
  * **Мова**: Python 3.12
  * **Веб-фреймворк**: FastAPI
  * **БД та ORM**: PostgreSQL 15, SQLAlchemy 2.0 (асинхронний режим), asyncpg
  * **Міграції**: Alembic
  * **Адміністрування**: SQLAdmin (доступ за адресою `/admin`, суперадмін `sadmin`)
  * **Черги та кешування**: Redis 7 (для збереження стану FSM у боті та обміну повідомленнями через Redis Streams)
  * **Планувальник**: APScheduler
* **Frontend**:
  * **Фреймворк**: Vue 3 (Composition API)
  * **Складальник**: Vite
  * **Стейт-менеджер**: Pinia
  * **Роутинг**: Vue Router
  * **Стилі**: Tailwind CSS 4
  * **API клієнт**: Axios
* **Telegram Bot**:
  * **Бібліотека**: Aiogram 3 (асинхронна робота з Telegram API)
  * **Збереження станів (FSM)**: RedisStorage
  * **API клієнт**: HTTPX (для запитів до FastAPI backend)

## 4. Базові інструкції щодо стилю коду для AI-агента

При внесенні змін до кодової бази системи дотримуйтеся наступних правил:

### 🐍 Python (Backend & Telegram Bot)
1. **Асинхронність**: Весь код має бути асинхронним (`async`/`await`). Не використовуйте блокуючі синхронні запити.
2. **Типізація**: Використовуйте анотації типів (Type Hints) для функцій, методів та змінних.
3. **SQLAlchemy 2.0**: Працюйте тільки в асинхронному режимі. Використовуйте новий стиль запитів через конструкцію `select()` (уникайте `session.query`).
4. **Робота з Redis**: Зберігайте стани користувачів боту у Redis. Зв'язок між бекендом та ботом має здійснюватися виключно через Redis Stream `vms_stream`.
5. **Форматування**: Код має відповідати стандартам PEP 8 (використовуйте `black`/`flake8` за наявності).
6. **Імпорти**: Усі імпорти — на початку файлу. Не імпортуйте модулі всередині функцій.
7. **Логування**: Завжди використовуйте налаштоване логування (`logging.getLogger(__name__)`) замість `print` у продакшн-коді.

### 🟢 JavaScript / Vue 3 (Frontend)
1. **Composition API**: Завжди пишіть компоненти з використанням синтаксису `<script setup>`.
2. **Управління станом**: Використовуйте Pinia для збереження станів та спільних даних (auth, requests тощо).
3. **Стилізація**: Для стилізації інтерфейсу застосовуйте класи Tailwind CSS 4. Уникайте написання ad-hoc або inline стилів без необхідності.
4. **Компоненти**: Створюйте перевикористовувані, чисті компоненти з чітко визначеними `props` та `emits`.

### 🌐 Загальні архітектурні патерни
* **Логування**: Завжди використовуйте налаштоване логування (`logging.getLogger(__name__)`) замість простих `print` у продакшн коді.
* **Безпека**: Не записуйте конфіденційні дані (паролі, ключі, токени) безпосередньо у код. Завжди використовуйте `settings` (змінні середовища).

## 5. Домашній глосарій (щоб агент не вигадував власні терміни)

### Статуси заявки (`Request.status`)
- `PENDING` — очікує рішення охорони
- `APPROVED` — підтверджена
- `REJECTED` — відхилена охороною
- `EXPIRED` — прострочена, автоматично проставляється планувальником

### Типи візиту
- пішохід, таксі, авто, кур'єр

### Ролі
- **мешканець** — користувач Telegram-бота, власник/орендар квартири
- **охорона** — оператор веб-дашборду, підтверджує/відхиляє заявки
- **sadmin** — суперадмін SQLAdmin, повний доступ до `/admin`

> Якщо потрібен новий статус, роль чи тип візиту — це архітектурне рішення. Спочатку запитай користувача, потім онови цей розділ і зроби запис у design log (розділ 8).

## 8. Design Log (`.agents/log/`)

Перед серйозною роботою над архітектурою — прочитай `.agents/log/index.md`. Шукай записи по зачеплених файлах і 2-3 ключових словах задачі.

- Записи зі статусом `done` — обов'язкові до виконання, не редагуй їх заднім числом.
- Записи `wip` — поточний напрямок роботи, онови при змінах.
- Новіші рішення переважають старіші; якщо бачиш конфлікт — повідом користувача, перш ніж продовжувати.
- Роби запис після значної архітектурної зміни (новий сервіс, зміна протоколу обміну між сервісами, новий статус тощо). Для рутинних правок (typo, дрібний рефакторинг) запис не потрібен.

**Назва файлу**: `.agents/log/YYYY-MM-DD-коротка-назва-kebab-case.md` (наприклад, `2026-08-03-meta-ads-migration.md`).

**Після створення запису обов'язково додай рядок в `.agents/log/index.md`** (найновіше — зверху):
```
- YYYY-MM-DD — Коротка назва рішення (wip|done)
```

**Шаблон вмісту запису**:
```markdown
# Коротка назва рішення

Статус: wip|done

## Рішення
Що саме вирішили зробити.

## Чому
Обґрунтування; які альтернативи розглядали і чому відкинули.

## Зачеплені файли/модулі
- ...

## 9. Формат коміт-повідомлень

```
<type>(<scope>): короткий опис до 40 символів

Довший опис — лише для значних змін, які потребують пояснення.
